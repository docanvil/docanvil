## Recommendation

Make V1.3 about OpenAPI documentation. Keep the first release focused on a complete static reference workflow; defer the WASM plugin system until there is evidence for extension points beyond templates and first-party generators.

API reference solves a concrete content gap: a team can now maintain guides, reusable examples and release snapshots in DocAnvil, but still needs a separate tool or manually maintained pages to describe its HTTP API. Plugins are infrastructure whose value depends on future use cases. Template components already address many of the presentation needs originally motivating them.

## Proposed V1.3 scope

Generate reference during the normal build rather than writing generated Markdown into the author's source tree. Reuse the site's page inventory and publishing pipeline so API pages behave like documentation pages. The initial implementation uses `[[openapi]]` with the existing build/serve/doctor/export commands; this section remains the full target scope, not a claim that every item is finished.

- Accept local JSON and YAML OpenAPI documents. Target 3.0 and 3.1, but publish a tested support matrix rather than claiming complete support for every schema dialect or keyword.
- Resolve internal and relative local-file references, report missing references with source context, and render recursive schemas without infinite expansion.
- Render API overview, servers, tag groups, operations, parameter location and requiredness, request/response media types, status codes, examples, deprecation and security requirements. Preserve authored Markdown descriptions through the existing rendering rules.
- Provide linked reusable schemas with types, constraints, composition and read/write distinctions within the declared support matrix. Surface unsupported constructs rather than silently dropping them.
- Give operations stable URLs and anchors, with a documented fallback when `operationId` is absent. Detect duplicate IDs and collisions with authored pages before output is published.
- Validate guide-to-reference links and generated operation/schema anchors. Allow deliberate navigation placement. Index operation names, paths and descriptions in search. Use existing theme conventions and template customisation.
- Load specifications from the selected version's source tree, including Git snapshots and their referenced files. Define locale fallback for a shared specification with translated surrounding guides; do not imply automatic translation of API descriptions.
- Include reference content in PDF, sitemap and AI-readable outputs. Define source attribution and dates for generated pages; edit links must point to the specification rather than an imaginary Markdown file.
- Watch specifications and referenced files in serve. Report parse errors, unresolved references, unsupported versions and URL collisions through build/doctor with consistent strict-mode behavior.

OpenAPI 3.0 and 3.1 require distinct schema handling; reference resolution also needs deliberate design. Use the official [3.0 specification](https://spec.openapis.org/oas/v3.0.4.html), [3.1 specification](https://spec.openapis.org/oas/v3.1) and [reference guidance](https://learn.openapis.org/referencing/overview.html) when settling the support matrix.

## Boundaries for the first release

Defer live “try it” requests, credential storage, SDK generation, API change detection, remote specification fetching, Swagger 2.0, GraphQL and AsyncAPI. The initial implementation reports unrendered callbacks/webhooks as warnings and rejects unsupported URI scopes, named/dynamic anchors and custom dialects. Any additional schema support needs an explicit supported-or-diagnosed decision. Remote Markdown includes remain separate from the remote code blocks already shipped.

A browser renderer may be useful later as an optional enhancement. The initial reference must remain readable without JavaScript and must contribute real content to search, PDF and AI outputs.

## Decisions made and remaining

Settled for the initial implementation:

- JSON uses Serde; YAML uses `serde-saphyr` 2.0. Preserve JSON-compatible values and reference identities instead of flattening schema dialects.
- One overview, one page per operation, and linked schema pages. Navigation can autodiscover the output namespace or operations folder, grouping operation links by tag without changing their URLs.
- Multiple `[[openapi]]` entries with independent namespaces. `spec` is relative to the selected content directory; optional `versions` limits an entry to enabled version names. A shared specification is repeated across enabled locales.
- Slugified operation IDs with collision errors; a deterministic method/path fallback when an ID is absent. Changing an ID changes its route, with redirects authored separately. Validate the policy against larger APIs before release.
- Render examples supplied in the specification. Do not synthesize requests or execute them in this slice.

The initial schema keyword/dialect presentation matrix and diagnostics are settled in the user guide. Still open: specification download/bundling policy; guide links beside operations; and whether locale-specific specifications or generated request examples are needed later. None requires a plugin framework first.


## Opportunities after OpenAPI

Keep the sequence focused: OpenAPI and its link validation first, reproducible sources next, then broader documentation quality. The following ideas are deliberately unscheduled and should be validated against actual projects before assigning releases.

| Idea | Reader or author benefit | Boundary to resolve |
| --- | --- | --- |
| API change reports | Understand changes between released specifications and write migration guides. | Distinguish structural changes from compatibility judgments; define comparison rules and version selection. |
| API documentation coverage | Find operations without descriptions, examples or documented errors. | Make quality rules configurable and separate from invalid-specification diagnostics. |
| Translation freshness | Find translations that lag behind changed source pages or included fragments. | Track the source revision reviewed by the translator; timestamps alone are insufficient. |
| Offline HTML bundles | Keep navigation and search available without hosting, alongside PDF. | Define file-URL versus local-server support and bundle scripts, fonts and diagrams. |
| Verified code examples | Catch examples that no longer compile or pass their documented checks. | Explicit opt-in execution commands, toolchains and CI environment; never execute arbitrary fenced code by default. |
| Documentation lifecycle metadata | Identify owners, review deadlines and deprecated or neglected guidance. | Extend optional metadata validation; Git modification dates do not establish a review. |
| URL migration audits | Find removed published routes before they break incoming links. | Compare output inventories, distinguish intentional removals and review redirect suggestions. |
| Search refinements | Distinguish conceptual guides from similarly named operations and schemas. | Assess relevance with realistic queries before adding aliases, weighting or filters. |
| Build provenance reports | Explain which revisions and inputs produced a published artifact. | Record local and remote dependencies without leaking machine paths or credentials. |
| Portable diagrams | Make Mermaid diagrams available offline and consistent across exports. | Evaluate renderer dependencies, reproducibility and accessible text alternatives. |
| Reusable content variables | Keep product names, release numbers and shared values consistent across prose. | Distinguish content substitution from theme variables; define escaping, version/locale scope and missing-value diagnostics. |
| Scoped lint suppressions | Allow justified exceptions without disabling checks across the project. | Specify page/line scope, require reasons where configured and flag unused suppressions. |
| Page discovery | Find published pages absent from navigation and help readers discover related guidance. | Distinguish intentionally unlisted pages; backlinks must respect versions, locales and draft visibility. |
| Selective exports | Produce a handbook or focused reference from selected chapters. | Define navigation-group selection, cross-links to omitted pages and shared asset inclusion. |
| Documentation change summaries | Help readers see what changed between releases beyond the API specification. | Distinguish content changes from formatting or shared-fragment churn; exclude drafts and link to authored migration guidance. |

These supplement existing ideas such as a glossary, remote Markdown includes, math, accessibility checks and external link checking. They are product opportunities, not claims that each capability is wholly absent or that demand has been measured. Avoid making them prerequisites for the first static API reference workflow.


## V1.3 usability candidates

Multiple local specifications with separate namespaces and API overview pages are implemented. Still evaluate downloadable specifications matching the selected documentation version, guide links beside operations, and whether tag ordering needs configuration beyond the specification’s own `tags` list. These are candidates for a usable first release; their final scope is not yet settled. Publishing a multi-file specification needs a deliberate download format and reference-path policy.

Generated cURL examples remain a stretch feature. Begin with specification-supplied examples; generated requests need correct parameter encoding, body handling and authentication placeholders. These candidates do not move the general ideas above into the V1.3 milestone.
